# 別AIレビュー依頼文（ChatGPTに貼るテンプレート）

使い方：下の枠内をコピーしてChatGPTに貼り、`review_bundle.md`（全ソース1ファイル）を添付する。
返ってきた回答は**そのままClaudeに貼るだけ**でOK。こちらで採用可否を判断し、修正・再テスト・コミットまで行う。

A/Bの2種類がある。**毎回両方やる必要はなく、1日1本、AとBを交互**で十分。

---

## A：コードレビュー依頼（技術面）

```
あなたはGoogle Apps Script（GAS）と業務システムのコードレビュアーです。
添付は、障害者グループホームを運営する会社の「記録の抜けを自動検出してLINEで確認するシステム（AI Uribo）」の
全ソースコードと仕様の要約です。GAS＋Googleスプレッドシート＋LINE Messaging APIで動きます。

【前提・制約】
- 実行環境はGASのみ（サーバー・DB・外部ライブラリなし）。データストアはスプレッドシート
- 運用するのは非エンジニア。エラーで止まらず、必ず実行ログに記録して処理を継続する方針
- 秘密情報はスクリプトプロパティのみ。コード・シートに置かない
- 利用者の氏名は台帳に置かない。医療・健康情報は扱わない
- GASのウェブアプリはHTTPヘッダーを取得できないため、X-Line-Signature検証は不可能。
  代わりにURLの秘密キー（?k=）＋スタッフマスタ照合で担保している（この制約自体は前提として扱ってよい）

【2026-08-13に追加された領域（ここは一度もレビューを受けていません）】
- `effect.gs` … センサー・カメラが役に立っているかを測る。**この数字で月々の課金を続けるか決める**ので、
  統計の取り方に誤りがあると経営判断を誤らせる
- `selfcheck.gs` の `checkSourcesAlive_` … 取込元ごとに「普段の間隔」を測り、
  長い沈黙を検知する。誤報が続くと現場が通知を読まなくなるので、誤報の出方を見てほしい
- `batch.gs` の `nightSendPlan_` / `nightBatch` … 夜勤者の勤務開始1時間前に送る。
  トリガーが1時間ごとになった影響（重複送信・取りこぼし）
- `ask.gs` の `referenceLogText_` … 自動データを質問に添える。複数件・拠点共通（ALL）対応
- `hub/homeassistant/ai_uribo.yaml` … Home Assistant側の設定（**GASではなくYAML/Jinja2**）。
  テンプレートの誤り、falseの検知、再起動直後の誤発火

【特に見てほしい観点】
1. 冪等性：同じ不足の二重検出、同じLINEの二重送信、同じ回答の二重記録が起きるパターン
2. 同時実行：朝バッチ実行中にLINE回答が来た場合など、LockServiceの掛け方の漏れ
3. GASの制限：6分の実行時間制限、1行ずつのシート読み書きによる性能劣化、
   UrlFetch/トリガーのクォータ。データが1年分たまったときに破綻する箇所
4. LINE Messaging APIの仕様違反：メッセージ数上限、テンプレートのtitle/text文字数、
   postbackデータ長、replyTokenの使い回し、X-Line-Retry-Keyの使い方
5. 日付・タイムゾーンの扱いの誤り（JST固定で書いている箇所の穴）
6. エラー処理：握りつぶしすぎ／握りつぶし不足、無限リトライの可能性
7. セキュリティ：なりすまし、情報漏れ、権限の広すぎるスコープ

【出力形式】
指摘ごとに次の形式で、重要度の高い順に並べてください。指摘が無い観点は書かないでください。
- 重要度：致命的／重要／軽微
- 該当ファイル・関数名
- 何が起きるか（具体的な再現条件）
- 修正案（コードで示せる場合はコードで）
最後に「このまま本番投入してよいか：はい／条件付きで可（条件を明記）／いいえ」を一行で。
```

## B：運用・監査観点レビュー依頼（現場面）

```
あなたは障害福祉サービス（共同生活援助＝グループホーム）の実地指導・記録実務に詳しいコンサルタントです。
添付は、記録の抜けを自動検出してLINEで担当者に確認するシステムの仕様と、実際に送られる質問文の一覧です。

【前提】
- 事業所：鹿児島県内のグループホーム（清水・玉里）。夜勤あり。夜間支援等体制加算を算定
- 記録は個別支援記録システム・業務日誌・実績記録票に分かれており、相互の整合が見られる
- 回答するのは現場スタッフ。回答は1〜2分で終わることを最優先にしたい
- 医療情報（診断名・病名・障害区分）は扱わない方針

【見てほしい観点】
1. 実地指導で確認される必須記録のうち、チェック項目（A1〜A7・B1〜B5）に抜けているものはないか
2. 逆に、監査上は不要なのに現場に聞いていて負担になっている項目はないか
3. 質問文の日本語：現場スタッフが迷わず答えられるか。利用者を傷つけない表現になっているか
4. 選択肢の設計：この選択肢で記録として成立するか。事実と推測が混ざらないか
5. 「わからない」と答えられた項目を週1回まとめて社員が確認する運用で、記録の完全性は保てるか
6. 自動データ（服薬センサー・開閉センサー・出勤情報）を人の記録の代わりにすることの是非と、
   記録上どう表現しておくべきか

【出力形式】
- 追加すべき項目／削るべき項目（それぞれ理由と根拠）
- 質問文の修正案（現行→修正後の対比で）
- 運用上のリスクと対策
根拠が公的資料に基づく場合はその旨を明記し、推測の場合は推測と明記してください。
```

## 返ってきたあとの流れ（Claude側の作業）

1. 指摘を1件ずつ **採用／不採用／要藤原様判断** に仕分け（不採用は理由を明記）
2. 採用分を修正 → `tests/harness.js` を再実行して53項目が通ることを確認
3. 仕分け結果を `docs/レビュー対応ログ.md` に追記してコミット
4. 「要判断」だけを藤原様にお返しする

## 添付ファイルの作り方

```bash
cd ai-uribo && bash tools/make_review_bundle.sh
# → review_bundle.md ができるので、それをChatGPTに添付する
```
（コードを更新したら作り直してください。Claude側でも都度お渡しします）
