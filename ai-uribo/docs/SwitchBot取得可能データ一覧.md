# SwitchBotから拾えるデータ一覧（AI Uribo接続の検討用）

調査日：2026-08-12／出典：SwitchBot公式API v1.1ドキュメント（デバイス別ページを直接確認）

**この一覧の使い方**：左から順に「どの機器が」「何を返すか」「AI Uriboのどの項目を埋められるか」。
埋められる＝**その項目は人に質問しなくなる**、ということです。推定で埋めたものは「要精査」が付きます。

---

## 0. 取得の2経路（両方使える）

| 経路 | 仕組み | 向いていること | 制約 |
|---|---|---|---|
| **ポーリング** | GAS から `GET /v1.1/devices/{id}/status` を叩いて現在値を取る | 温湿度・電力・施錠状態など「今どうなっているか」 | 1トークンあたり1日10,000リクエストが上限（要確認）。1日数回なら余裕 |
| **Webhook** | 変化した瞬間にSwitchBot側からURLへPOSTされる | 開閉・人感・施錠など「いつ起きたか」＝**時刻が要る記録** | 設定できるURLの数に制限あり（要確認）。AI UriboのWebhook URLをそのまま使えます |

**時刻が要るもの（開閉・人感・施錠・服薬ボックス）はWebhook**、
**状態が要るもの（温湿度・照度・電力）はポーリング**、という使い分けが基本になります。

| **温湿度計 Pro CO2** | 上記＋`CO2`（0〜9999ppm） | ○ | 上記＋**換気の記録**（新設候補）。CO2上昇＝換気不足の材料 | 高 |
| **漏水センサー**（Water Leak Detector） | `status`（0=dry / 1=leak） | ○ `detectionState`（0/1） | **緊急時・異常時対応**への自動通報（漏水を検知したら社員へLINE） | 高 |

## 4b. カメラ（要注意：公式APIからはデータが取れません）

**結論：SwitchBotのカメラは、公式Open APIでは「一覧に名前が出るだけ」です。**
状態取得なし・操作コマンドなし・Webhookなし。つまり **AI Uriboが自動で拾えるデータはゼロ**です。

| 機器 | APIから取れるもの | Webhook | AI Uriboで埋められる項目 |
|---|---|---|---|
| 屋内カメラ（Indoor Cam） | `deviceId` `deviceName` `deviceType` `enableCloudService` `hubDeviceId` のみ（＝機器の名前だけ） | ✕ | **なし** |
| 首振りカメラ（Pan/Tilt Cam・2K・Plus 2K/3K） | 同上 | ✕ | **なし** |
| **ビデオドアベル** | `battery`、`online`＋コマンド（動体検知のON/OFF） | **○** `detectionState`（DETECTED/NOT_DETECTED）、`press`（呼び出しボタンが押された）、`timeOfSample` | **来訪の時刻**／家族・関係機関との連絡の裏付け／玄関の出入り |

### 🔑 玉里ではもう「言葉」になっています（実機確認済み・2026-08-12）

実機の画面を確認したところ、玉里の **Pan/Tilt Cam Plus 3K FB** ＋ AIハブで、
すでに次の3つが動いていました。**APIを待たずに今日から使えます。**

| 機能 | 中身 | AI Uriboでの使い道 |
|---|---|---|
| **AIできごとログ** | 時刻つきイベント＋自然文の「できごと分析」<br>例：「男性が台所のシンク付近に立っており、手元を確認しながら何かを操作している様子です」 | 時刻つきの行動記録。将来の自動連携の本命 |
| **AIまとめ** | **日ごとの要約文**<br>例：「玉里のキッチンや部屋で、高齢の男性が食事の準備や調理、食器の洗い物、冷蔵庫の整…」 | **これをコピペするだけで、その日の記録が埋まる**（実装済み） |
| **発動条件（カスタマイズ）** | 自然文で条件を書くとシーン検知して通知<br>例：「利用者二人の、食事」 | 通知の文面をAI Uriboに渡せば、狙った項目だけを拾える |
| 検出トグル | 動物／家具／家電／物体／人／乗り物／**食べ物（ON）**／指定対象／顔 | 「人を検出」をONにすると在室・離床の材料が増える |

#### 今日からできること：LINEに貼るだけ

社員がLINEで **`まとめ`** と送り、SwitchBotアプリの「AIまとめ」の本文を**そのまま貼り付ける**と、
AI Uriboが取り込んで記録に反映します（実装・テスト済み）。

```
まとめ
↓
2026/08/07 この時期、高齢の男性が床に座り込んだりうつ伏せに…（貼り付け）
↓
取り込みました（2026-08-07分）。
この文章から 2件を記録に反映しました（うち推定 2件）。
※気になる記述があったため、社員に別途お知らせしました。
```

- 先頭の日付（`2026/08/07` や `8/7`）を対象日として読みます。無ければ昨日扱い
- S3チェック項目マスタの**「検出キーワード」列**に書いた語が文章にあれば、その項目を推定で埋めます
  （食事提供←食事・配膳・調理・食器／入浴←入浴・風呂／服薬確認←服薬・薬を／利用者の状況←座り込・うつ伏せ・転倒 …）
- 記録に残すのは**該当箇所の抜粋だけ**（全文は残しません）
- **注意語**（S8設定 `alert_keywords`：転倒・倒れ・うつ伏せ・座り込・出血・救急・発熱・嘔吐・痙攣）が
  見つかると、**社員へすぐLINEで知らせます**

> 8/07のまとめにあった「床に座り込んだりうつ伏せになったりする様子」は、まさにこの注意語に当たります。
> 記録として残すだけでなく、**その場で人に気づいてもらう**ための仕組みです。

#### ⚠ AIが書く文章は当てにしない（実機で確認）

現物を見ると、できごと分析の文章は**かなり粗い**です。
「男性が台所のシンク付近に立っており、手元を確認しながら何かを操作している様子です」——
何をしているかは分かりません。8/07の「床に座り込んだりうつ伏せになったり」も、
実際は屈んだだけかもしれません。**文章をそのまま記録にしてはいけない**、というのが結論です。

そこで実装をこう変えました：

- 注意語を見つけても**断定しません**。「AIが書いた文章です。**誤りが多く含まれます**」と明記して知らせます
- 通知には **[事実だった] [これは違う（誤検知）] [判断できない]** のボタンを付けました
- 押した判定はS10に貯まり、**週次ダイジェストに「AIの読み取り通知：n件（うち誤検知 m%）」**が出ます
- 誤検知が多い語は、S8設定の `alert_keywords` から外せます（現場で調整できる）

**文章は「人が見に行くきっかけ」であって、記録の中身ではない**——この線引きで運用します。

#### 🔧 本命は Frigate ＋ Home Assistant（設定画面にありました）

が並んでいます。これは大きい。

| 何が載っているか | 何ができるか |

**推奨する構成**：


これなら**文章の質に左右されません**。「18:05にキッチンで人を検知」は事実として扱えます。
言葉が要る部分（何をしていたか）だけAIの文章を参考にし、判断は人に任せる——
役割分担がはっきりします。

### 🔑 AIハブ（OpenClaw対応）でカメラの制約を回避できる仕組み

**これが今回いちばん大きい発見です。**
SwitchBotのAIハブは **OpenClaw**（AIエージェント）に対応していて、
**カメラ映像をVLM（視覚言語モデル）が解析し、状況を"言葉"にして**チャットアプリへ流せます。
（公式の例：ドアホンが来客を検知 →「配達員の方が荷物を持って立っています」と提案）

つまり——**APIから映像は取れなくても、映像から読み取った"言葉"なら取れる**。
AI Uriboは言葉さえ受け取れれば記録に落とせます。玉里のキッチンカメラが一番よく写るなら、
そこが最初の接続先になります。

| できること | AI Uriboで埋まる項目 |
|---|---|
| 「18:05に配膳している」 | **食事提供** |
| 「朝食の片付けが済んでいる」 | 食事提供・生活の様子 |
| 「◯時に居間の照明が点いた」 | 起床時刻 |
| 「来客対応をしている」 | 家族・関係機関との連絡 |

**受け口はもう実装してあります。** AI UriboのWebhook URLに、次の形でPOSTするだけです
（`?k=` 付きのURLをそのまま使えます）。

```json
{
  "source": "openclaw",
  "observations": [
    { "date": "2026-08-11", "target": "ALL", "item": "食事提供",
      "value": "夕食を配膳している様子（キッチンカメラ 18:05）" }
  ]
}
```

- `target` は `user_code`（例 `SMZ01`）か、拠点全員なら `"ALL"`
- `item` はS3チェック項目マスタの項目名（`食事提供` `在否確認` など）
- **画像・映像は送りません。言葉だけ**。台帳に残るのも言葉だけです
- 届いた内容は翌朝の自動充足で「推定（要精査）」として記録に入り、`精査` コマンドで一覧できます

**接続方法の候補**（実機で試して確定させたい部分）：

1. **OpenClawのSkillからHTTPを叩く** — 最短。上のJSONをPOSTするSkillを1つ作るだけ（**要検証**）
2. **Home Assistant経由** — OpenClawはHome Assistantを横断制御できるので、HA側のオートメーションでPOST
3. **LINEに流して人が転記** — 暫定。OpenClawはLINE対応なので、まずは目視で確認するところから

**ローカルLLM（Llama 3.2など）で完全ローカル運用もできる**とされています。
これができれば**映像は家の外に出ず、外に出るのは言葉だけ**になります。
グループホームで映像を扱ううえで、これは大きな利点です。

### では、カメラをどう活かすか（AIハブが無い拠点）

**経路A：RTSP（玉里のキッチンは対応を実機で確認済み・2026-08-13）**
玉里の **Pan/Tilt Cam Plus 3K FB** は、アプリの
**設定 → サードパーティーサービス → Home Assistant連携**から
**RTSPアカウント（ユーザー名／パスワード）を発行できる**ことを現地で確認しました。
＝ Frigate や OpenClaw が**ハブの中で映像を直接読める**ということです。
古い機種・無印は非対応で、公式アプリからしか見られません。

RTSPを使うときの決めごと（SwitchBot公式の注意書きに沿う）：

- **パスワードはSwitchBotアカウントと別のものにし、ランダムな16文字以上**にする
- **RTSPのURL（ユーザー名とパスワードを含む）は秘密情報**として扱う。
  チャットにも台帳にも貼らず、Apps Scriptのスクリプトプロパティか
  Frigateの設定ファイルにだけ置く
- ルーターで**外向きにポートを開けない**（玉里のLANの中だけで使う）
- 使わない期間は機能をOFFに戻す
RTSPが使えるなら、**常時起動のMac（または清水NAS）側で録画・定時スナップショット取得**ができます。
その場合もAI Uriboの台帳に入れるのは「映像あり／なし」の印だけにし、**画像そのものは台帳に置きません**
（利用者の個人情報になるため。台帳は氏名も置かない方針です）。

**経路B：ドアベルがあるならWebhook**
ビデオドアベルだけは他のセンサーと同じようにWebhookが飛びます。玄関に付いていれば来訪記録が自動で残ります。

**経路C：同じ目的なら人感センサーの方が安い・確実**
カメラで見たいこと（在室・離床・夜間の様子）は、**人感センサー／Presenceセンサーなら数値として取り込めます**。
カメラは「後から人が見て確認する」ためのもの、センサーは「記録として自動で残す」ためのもの、と役割が分かれます。

### プライバシーについて（実務メモ）

- 居室内のカメラは**本人・家族の同意と、設置場所・録画範囲の整理**が前提になります。共用部とは扱いが別です
- AI Uriboは映像・画像を一切扱いません（台帳に入るのは「記録があるか」だけ）
- 機器のIPアドレス・MACアドレスは、共有する相手を絞ってください（ネットワークに入る手がかりになります）

## 6. Uriboで今すぐ効きそうな順（費用対効果）

1. **服薬ボックスの開閉センサー（既存）** — 服薬確認。**すでに稼働中**
2. **玄関の開閉センサー or スマートロック** — 在否確認と**外出・帰宅時間**が丸ごと自動になる。
   A1（在否）とB2（外出・帰宅）の2項目が消えるので、質問削減の効果が最大
3. **居室の人感／Presenceセンサー** — 夜間巡回・就寝確認の裏付け。
   夜勤さんが一晩に何度も見に行かなくても「動きがあった／なかった」が残る
4. **Hub 2（照度つき）** — 消灯・点灯から**就寝・起床の時刻**が推定できる。室温・湿度も同時に取れる
5. **温湿度計** — 居室環境。夏冬の体調変化を「暑かった／寒かった」ではなく数字で残せる
6. **プラグミニ（電気ポット等）** — 起床・生活リズム。安価で効く

## 7. これを入れると新しく作れる記録項目（提案）

現在のS3チェック項目にない、**機械だけで埋まる**項目です。人への質問は増えません。

| 新項目（案） | 埋まる元 | 何の役に立つか |
|---|---|---|
| 起床時刻・就寝時刻 | 照度・カーテン・人感 | 生活リズムの変化＝体調・精神状態の予兆をつかむ |
| 居室環境（室温・湿度） | 温湿度計・Hub2 | 熱中症/低体温の予防。「暑い日に体調を崩した」の裏付け |
| 戸締まり確認 | スマートロック | 夜間の安全確認の記録 |
| 夜間の覚醒回数 | 人感・照度・開閉 | 不眠・頻尿の把握。支援の見直し材料 |
| 外出・帰宅時刻 | 玄関の開閉・ロック | B2が自動化。無断外出の早期把握にも |
| 設備異常 | 漏水・ロックのJAMMED | 発生した瞬間に社員へLINE |

## 7b. 【実装済み】SwitchBot本体との連携（switchbot.gs）

**もう作ってあります。** トークンを入れれば動きます。

### 使い始めるまで（4手）

1. [SwitchBotアプリ → プロフィール → 設定 → アプリバージョンを10回タップ → 開発者オプション]
   から **トークン** と **クライアントシークレット** を取得
2. GASのスクリプトプロパティに `SWITCHBOT_TOKEN` / `SWITCHBOT_SECRET` を入れる
   （あわせて `WEBAPP_URL` に `?k=` 付きのウェブアプリURLを入れる）
3. メニュー「AI Uribo」→ **「SwitchBot機器を読み込む」** → S12_機器マスタに全機器が並ぶ
4. S12で **拠点・対象user_code・用途種別** を確認し、**有効=TRUE** にする
   → メニュー「**SwitchBotのWebhookを登録**」を実行

### 何が動くか

| 仕組み | いつ | 何を取るか |
|---|---|---|
| **ポーリング** | 毎朝9:00（朝バッチの前） | 温湿度・CO2・施錠状態・消費電力・漏水。**電池残量20%以下は警告** |
| **Webhook** | 変化した瞬間 | 開閉・人感・施錠・漏水。**22時〜5時の検知は「夜間◯◯」として別項目に記録** |
| **漏水** | 検知した瞬間 | 社員へ即LINE通知 |

### S12_機器マスタの「用途種別」

ここに書いた言葉で、その機器のデータの扱いが決まります。

| 用途種別 | 何に効くか |
|---|---|
| `服薬ボックス` | 服薬確認（推定） |
| `玄関` | 外出・帰宅時間 |
| `居室ドア` | 在否確認・夜間の動き |
| `人感` | 在否確認・夜間巡回（推定） |
| `温湿度` | 居室環境（実測値） |
| `施錠` | 戸締まり確認（推定） |
| `家電` | 生活リズムの材料 |
| `漏水` | 即通知 |

機器名から自動で推測して初期値を入れますが、**必ず人が確認してから有効化**してください
（用途を間違えると、違う項目が埋まってしまうため）。

**deviceMac** をアプリの「デバイス情報」から転記しておくと、Webhookが利用者に紐付きます。
（ポーリングだけなら不要です）

## 8. 実装するとしたら（技術メモ）

- **認証**：v1.1はトークン＋シークレットで署名（HMAC-SHA256）を作る方式。
  GASの `Utilities.computeHmacSha256Signature()` で作れるので**追加ライブラリなしで実装可能**
- **ポーリング**：`GET /v1.1/devices` で機器一覧 → `GET /v1.1/devices/{deviceId}/status` で現在値。
  朝バッチの前（例：9:50）に1回走らせてS4に生ログを書けば、そのまま自動充足に乗ります
- **Webhook**：SwitchBot側に登録するURLは、AI Uriboの `?k=` 付きURLをそのまま使えます。
  受け口（doPost）で「LINEからの `events`」か「SwitchBotからの `eventType`」かを見分けて振り分ける形になります
- **秘密情報**：トークン・シークレットはスクリプトプロパティに保存（`SWITCHBOT_TOKEN` / `SWITCHBOT_SECRET`）
- **電池残量**：多くの機器で `battery` は 10/20/60/100 の4段階。**電池切れの予兆通知**にも使えます
