# AI Uribo（Phase0＋Phase1）

Uriboグループの各アプリのデータの抜けを自動検出し、LINEで担当者に確認して埋める常駐システム。
GAS＋Googleスプレッドシート＋LINE Messaging APIで構築。Macが閉じていても止まらない。

## このシステムの位置づけ（最重要・2026-08-12確定）

AI Uriboは**記録を正しく作る装置ではなく、記録者と利用者の実態を素早くつかむための補助**です。

- **帳簿の隙間は、手元にあるあらゆるデータを使って積極的に埋めにいく**
- 推定で埋めたものには **「要精査」** の印を付ける
- そのデータを見た現場の人が、さまざまな可能性を理解したうえで支援し、必要なら記録を直す
- **記録は記録、支援は支援。** 精査するのは人であって、AI Uriboの仕事は隙間を残さないこと

この方針は `src/autofill.gs` の冒頭にも書いてあります。実装で迷ったときはここに戻ってください。
（推定を止めたいときは S8設定の `autofill_estimate` を FALSE にすれば事実だけになります）

- 仕様の正：01〜08の仕様書キット。**【08】v1.1が最新の確定仕様**（矛盾する箇所は【08】を優先）
- 実装ステータス：Step1〜Step5のコード実装完了
- 検証ステータス：**ローカル自動テスト86項目すべてOK**（`docs/テスト結果報告.md`）。
  別AIレビュー第1回（技術面）の指摘13件は全件対応済み（`docs/レビュー対応ログ.md`）。
  運用・監査観点のレビューも実施し、質問文・選択肢を改善（`docs/運用監査レビュー.md`）。
  実機での動作確認（LINE表示・Webhook・Drive・トリガー発火）は `docs/テスト手順書.md` で人間が実施

## 確定した稼働スケジュール（【08】v1.1）

| 時刻 | 処理 | 内容 | 送信先 |
|---|---|---|---|
| 毎日 10:00 | `morningBatch()` | 自動充足 → 不足検出 → まとめ確認 | Stage1は藤原様・服部様の2名 |
| 毎日 21:00 | `nightBatch()` | 夜の確認セット（昨日の穴＋明日の予定） | 夜勤担当（居なければ社員） |
| 日曜 10:00 | `weeklyDigest()` | 週次ダイジェスト＋精度指標 | エスカレーション先社員 |
| 毎日 03:00 | `dailyBackup()` | Driveへ日次バックアップ | （失敗時のみLINE通知） |
| 毎日 07:00 | `flushQueue()` | 深夜帯に保留した送信を流す | — |

※17:00エスカレーションは【08】で廃止。

## 導入順序

1. `docs/STEP0_CHECKLIST.md` の準備を済ませる
2. `docs/デプロイ手順.md` に沿ってコードを配置し、`initSheets()` を実行
3. スクリプトプロパティを設定し、ウェブアプリとしてデプロイ → LINEのWebhook URLに設定
4. S1の登録コードを本人に伝え、LINEで送ってもらって紐付ける
5. `installTriggers()` を実行
6. `docs/テスト手順書.md` の10シナリオを実施して結果を記録
7. 別AIレビュー＋人間の動作確認を通過してから本番運用へ

## 設計上の約束

- 秘密情報（LINEトークン・シークレット）はスクリプトプロパティのみ。コード・シートには置かない
- スタッフの紐付けは登録コード方式（管理者が本人にだけ伝える8桁・使い捨て）。なりすまし登録を防ぐ
- Webhookは秘密キー未設定なら全拒否（設定漏れが認証無効化にならないようにする）
- 書き込みを伴う処理は全てロック内で直列化する（取れなければ処理しない）
- 利用者の氏名は台帳に載せない（S2はuser_codeのみ。氏名はS9対応表で管理し閲覧範囲を最小化）
- 診断名・病名・障害区分などの医療情報は扱わない
- 既存アプリの正本データは書き換えない。補完データはS7補完台帳に積み、既存アプリ側が取り込む
- 1件の失敗で全体を止めない（すべてS10に記録して処理継続）
- 同じ不足・同じ質問を二重に送らない（S5・S6で冪等性を担保）
